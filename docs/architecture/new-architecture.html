OpenAgent 新架构方案

基于 2026-10-13 ACP Runtime 文档包 + 历史代码 workspace/projects/OpenAgent(main @ 045c134,2026-10-08)整理 · 2026-10-14

结论。把"MAF 推理循环绑在 Engine/Core 里"改成"平台控制面 + 隔离 Worker + 可换 harness"。平台保留身份、会话、授权、审计、文件与 C# 业务服务;模型循环、上下文压缩、原生工具编排交给 ACP harness;C# 工具通过 MCP 网关继续复用。现有前端与 HTTP/SSE 接口先不动。

不熟悉技术术语?先读下面的「先读这里」,遇到陌生词查页面末尾的「术语表」。每个章节开头有一句「通俗说」。

先读这里

一句话:今天 OpenAgent 自己养着一个"AI 大脑"(MAF)并亲自指挥它干活。新方案让平台只当前台、保安和账房,把 AI 大脑换成可以随时更换的外部"专业工人"(harness),让他们在隔离的独立房间里干活。平台管身份、记录、权限和文件,不管工人具体怎么思考。

用一个比喻看全貌

把平台想成一家咨询公司:

公司里的角色对应方案里的负责什么
前台Router接待客户,判断该找哪位顾问,控制同时接待的人数
总务处Control核对客户身份、登记每次委托、记账留档、发放"门禁卡"、批准或拒绝敏感操作
独立工作间Worker + 隔离容器每位客户一间互相看不见的房间,顾问只能在自己的房间里工作
顾问harness(OpenCode、Gemini CLI 等)真正思考和动手的人,可以随时换人
内部服务窗口MCP 网关顾问要查客户档案、调公司内部系统,只能通过窗口办理,而且必须出示门禁卡
电话总机模型网关顾问要打电话请教大模型,必须经总机转接,总机核验身份后转接
门禁卡RunGrant只在这次委托期间有效的临时凭证,写明"这位客户、这次任务、能做什么"
房间使用借据租约房间使用权的临时借据,到期没续就收回,防止两个人同时占一间房
下班拍照存档快照每轮结束把房间里的文件柜拍照存好,房间出问题可以在另一间还原

一次请求是怎么走完的

  1. 用户在现有聊天界面发一条消息,前台(Router)判断交给哪个 Agent。
  2. 总务处(Control)确认用户身份和权限,登记这次任务,发出门禁卡。
  3. 总务处把任务放进队列,一间空闲的工作间(Worker)来领取,并把上次的快照还原进去。
  4. 工作间里启动顾问(harness),顾问开始思考,过程中的每个动作都实时回报总务处并入库。
  5. 顾问需要查资料或调业务系统时,通过MCP 网关办理;需要大模型时,通过模型网关。两处都核验门禁卡。
  6. 遇到敏感操作(比如写数据),任务暂停,等人在界面上批准或拒绝。
  7. 结果回到聊天界面;工作间拍下快照,门禁卡作废,房间回收。

什么变,什么不变

变不变
AI 的"思考循环"由外部 harness 承担,可更换;每个会话在隔离环境里运行;出现了 Worker、网关、租约等新部件现有前端和接口;平台的会话记录、用户权限、审计;已有的 C# 业务函数(通过窗口继续被调用)。MAF 执行路径不保留,harness 就绪后整体移除

1. 基线与范围

文档包是未来规划,历史代码仓(main @ 045c134)是研发起点。本方案以文档的目标设计为方向,以代码仓的真实结构为基础,逐模块标注 已有(直接复用)、改造(在现有代码上拆分或去耦)、新建(历史代码里没有)。

代码仓里没有任何 ACP 相关代码,Worker、RuntimeBinding、MCP 网关、租约与 fencing 也都不存在,这些都要新建。文档里提到的 PR #229 预览代码不在本地仓库,只当设计输入,不作为实现基线。

2. 目标架构

整张图像一栋大楼:用户从最上层进来,每一层只和相邻的下一层打交道,最底层是数据库等存储。上层不需要知道下层怎么实现的,就像你不需要知道电梯怎么造的。

分层视图

彩色大框是大分层(域),框内是七个层。蓝色底的小框为需要新建或重点改造的模块。整个系统是一条自上而下的单向链:每一层只向下调用,harness 访问 MCP 网关也是向下调用。

大分层:四个域

域包含的层一句话部署位置
入口域接入层、网关层用户的请求进来,先认证、判断交给哪个 Agent前端 + Router 进程
控制面应用层平台决策:准入、任务、租约、审批、配置,并留下记录Control 进程
执行域运行时层、执行层、能力层Agent 真正干活的地方,以及它能用的业务能力和模型运行时与执行层在 Worker 容器;能力层在 Control 进程内
基础设施域基础设施层状态与外部依赖:数据库、对象存储、缓存、模型、日志部署环境

下层对上层透明。上层只依赖下层暴露的契约,不知道下层的实现;下层不引用上层,结果和事件通过上层或 Contracts 定义的接口向上回传。分层是编译期依赖关系,与进程如何部署无关(能力层网关与应用层同在 Control 进程)。

层向上层暴露的契约对上层隐藏的内容
网关层统一入口 API、路由结果Engine 实例、哈希环、降级细节
应用层Run API、RuntimeEvent 流用的是哪种 runtime / harness、租约与存储实现
运行时层IRuntimeAdapter(Create/Execute/Cancel/Restore/Dispose)具体用哪个 harness、进程命令
执行层ACP 协议 + 标准 MCP 客户端行为模型循环、上下文压缩、原生工具编排
能力层MCP 工具 schema + RunGrant 校验C# 服务、DI、数据库、文件存储
基础设施Application / Capabilities 定义的仓储与存储接口PostgreSQL / Redis / 对象存储的具体实现

由此得到几条硬约束:Application 不出现 ACP / harness 类型;Runtime 不出现 Application 或数据库类型;Infrastructure 实现上层定义的接口,自己不被上层以具体类型引用;新增 harness 或存储实现时,上层代码不变。

调用与部署视图

首版 3 个部署单元:Router、Control(Application + Gateway)、Worker。每个进程内部同样自上而下分层,层间依赖遵守第 4 节依赖规则;跨进程只经协议:HTTP(Chat API)、Worker 协议(第 6 节)、MCP。Worker 的出站箭头表示它主动连接 Control,Control 不连 Worker。

外层支撑:审计、对话日志与可观测

这是围在整个系统外面的"记录层"。各层只管往里写记录,不会读取这些记录来决定业务;这样业务代码不依赖日志系统,日志系统出问题也不会拖垮业务(下面写明哪些情况例外)。

能力记录什么谁写入存放谁能查注意
审计中心谁、何时、对哪个资源、做了什么、结果如何:准入与授权决策(含拒绝)、门禁卡签发与撤销、MCP 工具调用(OperationId、参数摘要、结果引用)、审批请求与决定、租约与 fencing 变更和拒绝、manifest 变更、文件下载/分享/删除Application、Capabilities.HostPostgreSQL 只追加表,不可修改;大结果存对象存储,表里留引用租户管理员查本租户;平台安全人员可跨租户harness 原生工具的内部步骤拿不到,必须在界面标注覆盖范围
对话日志用户消息、助手回复、工具调用与结果摘要、审批记录、附件引用,以及 runId、traceId、runtime 与版本。用于前端历史回看和问题复盘Application(事件写入)PostgreSQL(对应现有 ConversationRecords);大内容存对象存储会话参与者看自己的会话;管理员按租户审查含用户内容,随租户的保留期和删除策略治理。与审计分开:对话日志服务业务回看,审计服务合规追责
模型交互日志每次模型请求与响应的元数据:模型、token、耗时、错误;内容可开关模型网关现有 LlmInteractionLogs平台排障内容需脱敏;harness 原生登录模式下拿不到,需标注覆盖范围
可观测性日志(Serilog)、追踪(traceId 贯穿 Router → Control → Worker → harness → 网关)、指标(Prometheus)、健康检查所有进程经 OTLP 到部署环境提供的 Collector、日志与指标后端运维日志中不得出现密钥、门禁卡和完整用户内容
安全事件与告警授权拒绝、旧 generation 被拒、路径逃逸尝试、Worker 异常失联各层产生,转为指标和审计记录指标与审计表运维、安全告警规则由运维按指标配置

记录层的规则

  • 单向旁路。Contracts 定义只写接口(IAuditSink、IConversationLogWriter),各层通过接口写入,实现在 Infrastructure。业务逻辑不读取审计表来做决定。
  • 写失败的处理分三档。会修改数据的工具调用:审计写不进去就拒绝执行(失败关闭)。对话与事件:先持久化,再向用户回显最终状态。可观测性数据:丢失可接受,不阻塞业务。
  • Worker 不直接写审计库。它只回传事件,由 Control 统一赋序号入库;Worker 本身只输出日志和追踪。
  • 脱敏。密钥、门禁卡、短期 key 永不入日志;审计里的参数只存摘要或哈希;对话内容的保留与删除跟随租户策略,备份一并治理。
  • 覆盖范围要说明白。平台事件、网关调用、模型网关请求是完整记录;harness 原生工具与内部推理步骤只有通知级别的记录,界面和审计报告里要标注。

4. 新项目目录与模块规划

把代码按职责分成不同文件夹和项目,并规定"谁可以调用谁"。目的是防止代码互相缠绕,以后换一个部件不用动其他部分。

沿用现有约定:OpenAgent.* 前缀、Backend/src + Backend/tests、集中包管理、文档统一进 docs/。不重命名现有项目(避免无谓 diff):Engine.Host 在迁移期承担 Control 宿主角色,稳定后再决定是否改名。

5. 关键设计决策

下面每一条都是一条"不能含糊的规矩",解释了为什么系统必须这样做。团队过方案时,重点看每条的理由有没有漏洞。

  1. 双层状态。平台会话/Run 存 PostgreSQL(历史、审计、裁决);harness 原生状态存独立持久卷。RuntimeBinding 记录 adapter/harness/version/nativeSessionId/workspaceId/stateRef/租约 generation,不只存 ACP sessionId。
  2. 身份走 RunGrant,不走模型参数。短期 token 绑定 subject/tenant/runId/workspaceId/leaseGeneration/expiresAt;网关每请求验签并查活动 Run,构造不可变 InvocationContext。McpClientPool 现按 tenant+url 共享,带用户委托的连接不能沿用。
  3. fencing 在写入端检查。租约失效的旧 Worker 必须在状态写入、MCP 写工具、产物发布和工作卷写入处被拒,Redis 锁本身挡不住它的副作用。
  4. 失败不自动重发 prompt。平台记录 OperationId、动作、资源、批准与结果;有幂等才重试,结果不明则核对。原生状态丢失就要求新会话,不悄悄把历史灌给另一个 harness。
  5. runtime 选择固定到会话。新会话可选 runtime;老会话绑定不变。切换只能显式新建会话并带授权摘要。
  6. 租约绑会话,不绑单次 Run。同一会话同一时刻只有一个活动轮次;Worker 持有会话租约直到空闲回收或被撤销,fencing generation 随会话租约递增。
  7. 状态位置:会话亲和 + 快照。调度优先把同一会话派回同一 Worker;每轮结束把原生状态与必要工作文件快照到对象存储,stateRef 指向最新快照。Worker 失联后在另一台 Worker 从快照恢复,不依赖本机盘。
  8. 模型经平台模型网关。平台编译模式下,harness 持短期 key 访问 Control 内的模型网关,密钥不进 Worker 容器;撤销和转发都在网关完成。Worker 容器出网只放行模型网关和 MCP 网关两个地址。harness 原生登录模式保留,不用于多租户。
  9. 审批是一等状态。ACP 反向权限请求映射为 AwaitingApproval,Control 提供审批 API 和超时/拒绝策略;决定经续租响应下发给 Worker。前端仅补最小审批入口。
  10. Admission 做能力匹配。会话需要的 MCP 传输、load/resume、Skill 装载、文件回调,对照每个 (harness, version) 的认证结果选 runtime,不满足直接拒绝,不等运行时失败。认证结果是随部署发布的 manifest 数据。
  11. Control 多副本:会话固定副本。Router 按会话把请求固定到同一 Control 副本,事件不做跨副本扇出;副本宕机后会话重新绑定,从持久化事件补发。
  12. 事件按粒度入库。增量事件按块合并后批量写;完整消息、工具调用、状态变更逐条写,以后者为权威记录。事件契约里显式区分两类。
  13. harness 版本不可变。Worker 镜像固定 digest,运行时禁止联网安装或自动升级;manifest 记录版本与兼容指纹。升级先让少量租户的新会话切换,老会话保持原版本。
  14. RunGrant 同进程也走 HTTP 验签。Control 用私钥签发,网关用公钥验证,harness 仍通过 /mcp HTTP 路径调用,不在内存里直接校验。这样路径与生产一致,将来拆出网关不改协议。
  15. traceId 贯穿全链路。Router → Control → Worker → harness → 网关用现有 OTel 传播;RunId、OperationId 作为日志与审计的公共关联键。
  16. 旧 API 兼容映射有明确归属。RuntimeEvent 到现有前端 SSE 的转换放在 Engine.Host 兼容 API 中,并用契约测试锁定当前前端的事件形态,前端冻结期间不漂移。
  17. 隔离靠部署边界。Worker 运行在容器里,容器是隔离边界(独立 HOME/XDG、出网白名单、资源限制),代码内不再包含沙箱后端。harness 的原生 Bash/读写能绕过 C# wrapper,所以完整进程树必须在同一容器内,ACP 权限回调只是附加策略。容器与会话的对应关系(一容器一会话,还是复用)待确定。

6. Worker 协议

Worker(工作间)和 Control(总务处)之间用什么"对讲规则"沟通:怎么领任务、怎么证明自己还活着、怎么汇报进展、怎么被叫停。规则越清楚,出故障时越容易判断谁对谁错。

Worker 不引用 Application 和 Infrastructure,所以它与 Control 之间只有一条窄协议。协议 DTO 放在 Contracts/Runtime/WorkerProtocol;Control 侧端点在 Engine.Host 的 Worker API,客户端在 Worker.Host/Leasing。传输沿用现有 HTTP + JSON,事件批量用 NDJSON;只有压测证明不够时才考虑 gRPC。

设计原则

Worker 只主动打电话给 Control,Control 从不打电话给 Worker。这样隔离区不需要对外开任何门。

  1. Worker 只出站,不开入站端口。Control 不需要知道 Worker 地址,Worker 位于隔离网络时不用开放反向入口。
  2. 所有控制指令搭在租约续期的响应里。取消、撤销、排空都不是 Control 主动推送,而是 Worker 在续租或长轮询时拿到。
  3. 事件至少一次、按序号去重。Worker 本地缓冲事件并带 (runId, seq),Control 去重并回 ackedSeq,Worker 收到 ack 前不丢弃。
  4. 每个请求都带 fencing generation。Control 发现过期 generation 返回 409,Worker 必须立即终止对应进程树。
  5. 租约属于会话。续租、fencing generation、取消都以会话为单位;领取时 Control 优先派给持有该会话快照或热状态的 Worker。
  6. 租约到期即自我隔离。Worker 超过 TTL 联系不上 Control,必须自行停止 harness,不能继续执行并产生无人记录的副作用。

Run 状态

一次任务(Run)会经历排队、领取、运行,最后是成功、失败、取消、等待批准或"中断待核对"。"中断待核对"表示工作间突然失联,系统不知道最后一步有没有做完,必须先核对再继续,不能直接重做。

状态进入条件出口
QueuedAdmission 通过(含能力匹配)Claimed
Claimed → Running领取成功;binding 已持久化后才提交 promptSucceeded / Failed / Cancelled / AwaitingApproval / Interrupted
Interrupted租约到期未续;结果待核对确认旧进程停止、旧 generation 被拒后,从最近快照在另一 Worker 恢复;结果不明的写操作人工或业务核对;不自动重发 prompt

建议初值(待压测,不是结论)

租约 TTL 30 秒,续期间隔 TTL 的三分之一;长轮询 25 秒;取消先发终止信号,宽限期后终止整棵进程树并回报。以上数值只是起点,以真实运行的实测为准。

必须验证

  • 续期丢包、Control 重启、Worker 断网超过 TTL:harness 被自行停止,无残留子进程。
  • 旧 Worker 在被取代后继续发事件、写产物、调写工具:全部被拒。
  • claim 重试、事件重复发送:无重复 Run、无重复事件。
  • 取消与完成同时到达:状态只收口一次。

7. 风险与待验证项

这里列的是我们目前没有把握的地方,需要先验证或做决定,不是已经发生的问题。

  1. Gateway 并入 Control 的代价。同进程后,网关与业务服务共享故障域和扩缩容;靠独立路由、独立 audience 和独立授权策略隔离,代码层面仍是独立项目(Capabilities.Host),保留以后拆出的可能。出现独立扩缩容或信任域需求时再拆。
  2. .NET 8 即将停止支持。仓库为 .NET 8(global.json、Directory.Build.props)。微软公告:.NET 8 与 .NET 9 均在 2026-11-10 结束支持,之后不再有安全更新;.NET 10 为 LTS。目标运行时定为 .NET 10(见决策记录)。MCP SDK 1.4.1、EF Core、ACP 协议库是否都支持 .NET 10 尚未验证,需在升级时逐一确认。
  3. ACP C# SDK 是非官方的。nuskey8/acp-csharp 个人维护,先做恢复、反向权限、断线取消的验证再决定是否替换现有协议代码;协议库必须封在 Runtime.Acp 内,契约不暴露其类型。
  4. harness 能力不对齐。DeepSeek Harness 只支持 resume、不支持 load,且为 developer preview;OpenCode 预览只支持 load。"自由切换 harness"只在认证过的能力矩阵内成立,不是通用承诺。
  5. 审计有缺口。harness 内部模型步骤和原生工具的完整输入输出拿不到。必须强审计的业务动作只能走网关,需在产品层说明覆盖范围。
  6. 隔离强度取决于部署。取消沙箱后端后,不同会话之间的隔离完全依赖容器配置:挂载范围、出网限制、资源上限、一容器对应几个会话。这些要在部署规范里写死并用反例验证(两租户同名会话、越界路径、原生 HOME 泄漏),否则隔离只停留在设计上。
  7. 容量与冷启动未知。隔离由容器提供,若采用一容器一会话且不跨租户复用,新会话会有冷启动延迟和固定内存占用。单会话启动耗时、单机并发上限、空闲回收时间需要实测,结果决定是否做同租户内的 warm 池,也影响成本估算。
  8. 前端冻结的代价。保持旧 API 兼容意味着需要兼容层(G05),长期要维护两套语义;应在 ADR 里写明退出条件。

议题决定理由与例外
PR #229 的 ACP 预览代码不复用。在本地 main 上按本方案自行实现;#229 只作设计输入和测试用例来源。它不在本地仓库,无法评审;文档已指出它在 Engine 进程内启动 harness、mcpServers 为空、混有 OpenCode 专用配置,与目标分层相反。例外:协议帧限制、失败分类、事件映射等独立小块,经评审后可逐块移植,不整体合并。
Capability Gateway 部署位置首版并入 Control 进程,代码上保持独立项目 Capabilities.Host。网关与业务服务同属受信域,单独部署只增加运维面,不增加隔离。拆分条件:出现独立扩缩容或独立信任域需求。
目标运行时.NET 10(LTS)。升级与功能改动分开提交。.NET 8 于 2026-11-10 结束支持(微软公告)。与重构混在一起会让回归无法定位。例外:若关键依赖(如 ACP 协议库)尚不支持 .NET 10,对该依赖单独评估,不阻塞其余升级。
隔离边界由部署的容器提供,代码内不含沙箱后端;MAF 执行路径直接移除,不并存、不保留回退。只保留一条执行路径,避免双套语义与维护成本。代价:harness 与 Worker 就绪前无法切流,移除须排在切换验证之后;隔离强度取决于容器配置,见风险。
Worker 传输协议HTTP + JSON,事件批量用 NDJSON,Worker 出站拉取。沿用现有技术栈,足够首版。仅当压测证明不够时再评估 gRPC。
审计与对话日志作为外层旁路记录层:审计中心、对话日志、模型交互日志、可观测性分开存放,各层只写不读。业务不依赖日志系统,日志出问题不拖垮业务。例外:会修改数据的工具调用,审计写失败则拒绝执行。
配置中心不新建配置中心(取消 Matrix 配置)。Agent 沿用 Engine 现有配置,增加 runtime 选择字段;harness 清单(manifest)作为随部署发布的静态数据。范围收敛。代价:没有按配置版本做快照与回滚的能力,runtime 清单变更走部署发布;Run 创建时记录当时的 manifest 版本用于追溯。
现有项目重命名不重命名。Engine.Host 兼任 Control 宿主。避免无谓 diff;稳定后再决定。
首批认证的 harnessOpenCode 先认证,Gemini CLI 作为第二个。DeepSeek Harness 仅试验,Claude bridge 仅 LocalTrusted 预览。两者为开源且文档已核对 ACP 入口;DSH 不支持 load 且为开发者预览;Claude 继承宿主登录不能作为生产身份方案。

这些是架构层面的决定,可被推翻。排期与人力不在本页范围,架构确认后另行规划。
